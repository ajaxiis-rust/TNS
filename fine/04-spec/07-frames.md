### F-01. Изоляция миров
Суть: Миры изолированы полностью. Порталы и уровни изоляции исключены.
Правила:
1. Между мирами нет прямых каналов связи.
2. Обмен данными между мирами выполняется только через Forge.
3. Порталы, телепорты между мирами и уровни изоляции не реализуются.
Связи: F-02
Приёмка: в схемах данных и коде нет таблиц, маршрутов или сущностей, соединяющих два мира напрямую; любой путь обмена между мирами проходит через Forge.

### F-02. Обмен между мирами
Суть: Единственный канал обмена между мирами — Forge. Входом служат только сырые книги в форматах txt и fb2.
Правила:
1. Между мирами данные переходят только через Forge; отдельных каналов мир-мир нет.
2. На вход Forge принимаются только сырые книги в форматах txt и fb2; прочие форматы конвертируются до ковки.
3. Сырьё живёт файлами в папке мира; в базы входит только выкованное.
4. Скачивание корпусов и внешних каталогов книг в состав станка не входит: файлы книг игрок скачивает сам и передаёт импортом.
Связи: F-01
Приёмка: импорт книги отклоняет любой формат кроме txt и fb2; запись из world-базы одного мира не может быть перенесена в world-базу другого иначе, чем через ковку Forge.

### F-03. Выходы мира наружу
Суть: Из мира наружу идут только два типа выходов: разведка Паганеля и внешние слоты моделей. Оба — по явному выбору владельца станка.
Правила:
1. Разведка пути Паганеля — норма работы: выполняется с разрешения и с тайм-аутом ~30 с; пропуск разведки не блокирует ход.
2. Внешние слоты моделей (Ткач, глубокий разбор, Редактор) применяются по явному выбору владельца станка.
3. Всё прочее остаётся в мастерской; иных путей наружу нет.
4. Живой контур физически не имеет доступа к ключу внешней модели Паганеля: ключ хранится только в карточке.
Связи: F-04, F-05, F-07, F-08
Приёмка: исходящий трафик станка сводится к разведке Паганеля (при включённом переключателе) и вызовам внешних слотов; иных исходящих соединений нет.

### F-04. Сеть
Суть: Станок работает только на исходящих соединениях; открытых портов нет.
Правила:
1. Допустимы только исходящие соединения: внешний API слота, HF для менеджера моделей, край Cloudflare для web-транспорта.
2. Входящих соединений и наружных слушающих сокетов нет.
3. Web-транспорт — туннель cloudflared: станок подключается к краю исходящим соединением, публичных портов нет.
4. Telegram выбран каналом, решающим NAT исходящим соединением.
Связи: F-05, F-06
Приёмка: приёмочная команда (ss -lntp против белого списка слушающих сокетов) не показывает наружных слушающих портов.

### F-05. Единый сетевой гейт
Суть: Один компонент кода перечисляет допустимые внешние адреса и блокирует любой другой исходящий запрос.
Правила:
1. Белый список гейта составляют адреса внешнего API слота и HF для менеджера моделей.
2. Любой исходящий запрос к адресу вне белого списка блокируется гейтом.
3. Гейт — единственный компонент, через который проходит наружный трафик станка.
Данные: белый список допустимых внешних адресов — конфигурация гейта.
Связи: F-03, F-04
Приёмка: попытка исходящего запроса к адресу вне белого списка отклоняется гейтом, в журнале присутствует запись об отказе.

### F-06. Проверка портов
Суть: Контроль слушающих портов выполняется при старте сервера и подтверждается приёмочной командой.
Правила:
1. При старте сервера слушающие сокеты сверяются с белым списком.
2. Приёмочная команда: ss -lntp сравнивается с белым списком разрешённых слушающих сокетов.
3. Слушающий порт вне белого списка — дефект; старт сервера с наружным портом вне списка не проходит.
Данные: белый список разрешённых слушающих сокетов.
Связи: F-04
Приёмка: команда ss -lntp не показывает сокетов, отсутствующих в белом списке.

### F-07. Приватность
Суть: Отправка прозы через внешнего провайдера — осознанный выбор владельца станка.
Правила:
1. Генерация прозы внешним слотом означает, что тексты проходят через внешнего провайдера.
2. Выбор внешнего слота делает владелец станка; дефолт — локальный пресет.
3. Словарный контроль пакета не зависит от слота и остаётся на стороне станка.
Связи: F-03
Приёмка: при локальном пресете внешних вызовов генерации нет; при пресете «внешние API» использование внешнего провайдера задано явной настройкой слота.

### F-08. Тексты мира в разведке
Суть: Для передачи текстов мира (пролог, описание) в разведке достаточно включённого переключателя «походы наружу»; отдельного запроса подтверждения нет.
Правила:
1. Тексты мира (пролог, описание) могут участвовать в разведке Паганеля.
2. Включённый переключатель «походы наружу» — достаточное разрешение на такую передачу.
3. Отдельного запроса подтверждения на каждый случай передачи нет.
4. При выключенном переключателе «походы наружу» наружу не уходит ничего.
Связи: F-03
Приёмка: при выключенном «походы наружу» разведка не выполняет внешних вызовов; при включённом — работает без дополнительных подтверждений.

### F-09. Деградация слота
Суть: Деградация внешнего слота видна владельцу станка пост-фактум в мониторинге, не только в журналах.
Правила:
1. Каждый случай ухода хода на запасной путь вместо внешнего слота фиксируется.
2. Мониторинг показывает деградации хода отдельным блоком.
3. Мониторинг — только чтение: кнопок, меняющих состояние станка, в нём нет.
Связи: F-07
Приёмка: экран мониторинга содержит блок деградаций хода; после отказа внешнего слота счётчик блока увеличивается.

### F-10. Анти-чит
Суть: Пауза не замораживает мир: в отсутствие игрока мир живёт той же скоростью. Реализация пауз заморозкой запрещена.
Правила:
1. Темп времени всегда 1:1: мир не смещается относительно игрока ни в игре, ни в паузах, ни во сне.
2. В отсутствие игрока мир живёт той же скоростью: обсчёты NPC работают, отложенные события срабатывают.
3. Возврат игрока даёт сводку «пока тебя не было» и запаздывающие вести.
4. Реализация пауз заморозкой состояния мира запрещена.
Связи: LT-11, LT-12
Приёмка: отложенное событие с дедлайном срабатывает во время отсутствия игрока; состояние мира после паузы отличается от состояния до паузы.

### F-11. Язык движка: Go
Суть: Ядро станка и однозадачные программы роя пишутся на Go; интерфейс игрока остаётся веб-интерфейсом в браузере.
Правила:
1. Ядро станка и задачи роя — Go (решение владельца 18.10); резидентные движки чужой сборки — llama.cpp-генерация и эмбеддинги — остаются собой, язык их не касается.
2. Доставка игрокам — компилируемые статичные бинарники без рантаймов и зависимостей: ни Python, ни Node на машине игрока не требуется.
3. Интерфейс игрока — веб: рендер на стороне браузера; карта «Прорисовка карты» рендерится интерфейсом (W-20).
4. Механические гейты кода движка: сборка, канонический формат (gofmt), статический анализ (go vet), тесты с детектором гонок (-race) — обязательная часть приёмки любого кода станка.
Связи: F-12, MD-01, W-20.
Приёмка: ядро и задачи роя собираются в статичные бинарники под целевые платформы; код движка проходит gofmt без расхождений, go vet и тесты с детектором гонок без ошибок.

### F-12. Три слоя станка: ядро-надзиратель, резиденты, рой задач
Суть: Станок = три слоя: ядро-надзиратель (один процесс-хозяин), резидентные сервисы горячего пути (постоянные дети ядра), рой однозадачных задач мастерской и кузницы.
Правила:
1. Ядро — единственный процесс-хозяин: держит конвейер живого хода, очередь мастерской, таймеры отложенных событий и приоритет хода игрока; порождает, лечит и останавливает остальные процессы станка.
2. Правило одного писателя: в оперативную базу мира пишет только ядро; задачи роя отдают результаты ядру и пишут только в отведённые им таблицы литературной базы; гонки данных исключены построением, детектор гонок — в гейтах (F-11).
3. Резидентные сервисы — постоянные дети ядра: генерация, эмбеддинги, лемматизатор. Запуск, лечение и остановка — обязанность ядра; готовность проверяется health-запросом без фиксированного короткого бюджета (загрузка модели — минуты); вывод процессов пишется в журнал станка, молчаливый вывод запрещён.
4. Рой задач: каждая ковка, доукомплектация, коллизия, оседание сцены — однозадачный запуск с началом и концом; завершился — результат в базу, процесс умер; между паузами в памяти ничего не висит.
5. Версии: ядро и задачи роя выпускаются одним пакетом; задача старой версии с ядром новой версии не запускается.
6. Один способ запуска: все процессы станка — дети ядра; запуск резидентов или задач «своей жизнью», в обход ядра, запрещён.
Связи: F-04, F-09, F-11, W-01, W-17, MD-03.
Приёмка: при падении резидента ядро перезапускает его с паузой и фиксирует деградацию в мониторинге; во время минутной загрузки генерации живой ход работает путями без LLM; завершённая задача роя не остаётся в памяти; второй запуск ядра не порождает дубликатов резидентов.
