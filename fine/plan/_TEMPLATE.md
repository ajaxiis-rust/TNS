# Формат задачи

Одна задача — один атомарный кусок работы. Агент-исполнитель читает задачу
целиком и не додумывает недостающее; если чего-то нет — задача не готова (DoR).

```markdown
### T-XX-NN. Короткое имя задачи
- **Атомы:** D-07, LT-09 (только ID из `fine/04-spec`); инфраструктура — рамка (F-12.5) без атомов.
- **Выдержки атомов:** 1–3 строки на атом — норма дословно из спеки; исполнитель не ходит в спеку.
- **Зависит от:** ID задач, закрытых до старта. Пусто — старт с начала волны.
- **Читать:** не более трёх файлов плана помимо этой задачи.
- **Создаётся:** `engine/internal/<пакет>/<файл>.go` — точный путь.
- **Правится:** точный путь; «нет», если ничего.
- **Писатель:** по карте писателей (T-01-07): `core`, `forge`, `sediment`, `bake`, `нет записи`.
- **Шаги:**
  1. Одно действие на шаг.
- **Проверка:** `cd engine && …команда…` → ожидаемый результат.
- **Исполнитель:** код / ядро станка / модель / владелец.
```

Правила заполнения:

1. **Атомы** — только ID из `fine/04-spec`, через запятую. Задача-инструмент
   ссылается на рамку (`F-12.5`) или помечается «инфраструктура» без атомов.
2. **Выдержки атомов** — обязательное поле: норма атома в 1–3 строки дословно.
   Исполнитель с малым контекстом не восстанавливает её из спеки.
3. **Зависимости и нумерация** — порядок исполнения задаёт «Зависит от», а не
   номер задачи. Новая задача получает следующий свободный номер своей волны
   (`T-02-15` после `T-02-14`); резать задачу можно через суффикс `a/b` только
   при явной правке всех ссылок на неё.
4. **Файлы** — путь от корня репозитория `TNS65/`. Все команды проверки
   выполняются из `engine/` и пишутся с префиксом `cd engine &&`. Пути без
   «примерно» и без глобов.
5. **Писатель** — идентичность из карты писателей T-01-07: `core` (живой ход и
   рождение таблиц хода), `forge` (места, пути, world_meta — пишет контур
   рождения, мастерской и Паганеля), `sediment` (осевшие записи), `bake`
   (base.db при запекании). Нужно для сквозного гейта «один писатель»
   (D-09.7, F-12.2).
6. **Шаги** — пронумерованные, один глагол действия на шаг. Никаких «и также
   не забыть»: каждый шаг проверяем.
7. **Проверка** — одна команда, которую можно скопировать в шелл, и ожидаемый
   результат словами: `exit 0`, «вывод пуст», «ровно 96 строк». Тесты Go
   запускаются с `-count=1`; тест с `-run` — через `scripts/runtests.sh <pkg> <TestName>`
   (падает, если у имени нет `PASS`). Проверка не требует интерактивности,
   живой сети и внешних сервисов: слоты, эмбеддер и часы подменяются
   `internal/testkit`.
8. **Исполнитель** — `код` (юнит-тест или команда), `ядро станка` (поведение в
   рантайме), `модель` (LLM-роль, проверяется по журналу и счётчикам через
   фейковый слот из testkit), `владелец` (только приёмочные сценарии P8 и
   решения вилок).

Роли пайплайна (действуют в каждой задаче, где есть код):

- тест пишет MiMo по полю «Проверка» **до** кода;
- код пишет DeepSeek, доводит тест до зелёного;
- ревьюит GLM: код и тесты отдельными диффами, ослабление теста — дефект ревью;
- три красные попытки подряд — задача в `blocked` с приложенным выводом
  проверки в `99-LEDGER.md`, без четвёртой правки вслепую.

Контрактный блок — разрешён и обязателен на границах:

- сигнатуры Go-типов, DDL таблиц, JSON-схемы обмена, формулы с числами и
  пороги — это контракты, а не реализация; задача обязана фиксировать их,
  когда создаёт тип, таблицу, формат обмена или пороговое правило;
- запрещено и дальше: тела функций и код реализации в тексте задачи,
  «и так далее», «аналогично», проверки вида «убедиться, что работает»,
  ссылки на память агента и на чат.

Запрещено в задачах:

- код реализации (план содержит действия и контракты, не реализацию);
- «и так далее», «аналогично» — задача описывается до конца;
- проверки вида «убедиться, что работает»;
- ссылки на память агента и на чат: всё нужное — в спеке и в этом плане.
