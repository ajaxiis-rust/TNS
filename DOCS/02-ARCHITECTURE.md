# 02 — Архитектура системы TNS65

> Карты контуров, ролей, данных и родословной. Источники: `TNS65-PARADIGM.md`, `TNS65-PARADIGM-draft.md` (шесть частей), `RAW/base.md`, `RAW/03-data-TNS35.md`, `RAW/04-runtime-TNS35.md`. Подробно о базах — `DOCS/05-DATABASES.md`.

---

## 1. Что за система

TNS65 — нарративный движок. Игрок ведёт диалог с миром через Telegram или web-клиент: каждая реплика становится абзацем, сессия — главой, книга собирается автоматически. Формула проекта: «Пиши свою книгу просто играя».

Под всем лежат два правила. Первое — State-First: состояние мира считает код, модель его только проговаривает, текст не переписывает outcome. Второе — гибридная рамка (п.1): рутина подаётся из банков без вызова модели, уникальное и эмоциональное пишет живая модель.

Зачем два правила, а не одно. State-First защищает факты: если бы текст мог менять исходы, один дрейф модели ломал бы канон книги. Гибридная рамка защищает время и стабильность: повторяемое выдаётся одинаково и быстро, живая модель тратится только там, где без неё не обойтись (п.3). Критерий успеха любой механики при этом один: книга становится интереснее для постороннего читателя, который не знает автора.

Пример. Игрок здоровается с торговцем на рынке — это рутина, фраза берётся из банка и уходит игроку за единицы секунд. Тот же игрок вечером просит надсмотрщика отпустить к матери после вчерашнего публичного оскорбления — это уникальная сцена конкретной пары героев, её пишет Ткач, ход занимает 30–60 с (канон, честная цена рамки).

## 2. Два контура

Система разделена на два контура по времени работы. Живой ход отвечает игроку, мастерская готовит материал в его отсутствие.

```
┌─────────────────────────────────────────────────────────────┐
│  ЖИВОЙ ХОД (рантайм)                                        │
│  игрок → Telegram/WSS → фасад :8000 → конвейер хода         │
│       → Челнок (банк) или Ткач (модель) → ответ игроку      │
│  Латентность: единицы секунд (рутина) / 30–60 с (пик)       │
│  Пишет: только world(name).db                               │
└─────────────────────────────────────────────────────────────┘
                              ↕ стоп-кран, приоритет хода
┌─────────────────────────────────────────────────────────────┐
│  МАСТЕРСКАЯ (паузы и ночь)                                  │
│  молчание игрока → ступени пауз → очередь ковки             │
│  Гефест / Паганель / Пифия → literary.db + world(name).db   │
│  Латентность: минуты–часы; окно ночи 8 ч                    │
└─────────────────────────────────────────────────────────────┘
```

Живой ход — всё от «игрок отправил реплику» до «мир ответил»: мост Telegram → фасад :8000 → конвейер хода → ответ игроку. Исполнитель — код конвейера и модель Ткача на пике; пишет только в `world(name).db`.

Мастерская работает в паузах и ночью. Молчание игрока меряется на сервере, открытая ступень задаёт допустимую тяжесть работ (п.7); очередь варки кормит Гефеста, Паганеля и Пифию. Латентность — минуты и часы, окно ночи — 8 ч (канон).

Зачем раздельные контуры. Ход игрока ждать не может, а фоновая варка требует длинных вызовов и тяжёлых просчётов. Поэтому ход игрока всегда приоритетнее фоновой варки (п.7). Незавершённая работа не вторгается в живой ход и не выбрасывается: следующий шаг ждёт следующей паузы, продолжение — с места остановки, не перезапуск.

Пример. Ночью мастерская куёт пробуждение следующей главы. Игрок неожиданно возвращается через двадцать минут — варка замирает на текущем шаге, живой ход обрабатывается сразу, а незаконченный шаг продолжится в следующую паузу.

## 3. Шесть частей круга игры

Парадигма читается по жизни книги, а не по списку механик. Шесть частей повторяют круг: станок до игрока → рождение мира → живой ход → пауза и ночь → глава и книга → постоянные рамки.

| Часть | Что происходит | Пункты |
|---|---|---|
| **I. Станок до игрока** | сменные модели, языковые пакеты, три базы, наследие симуляции | п.14, 20, 15 |
| **II. Рождение мира** | анкета, пачка персонажей, якорь сценарной рамки | п.13 (рождение), 21 |
| **III. Живой ход** | реплика → ответ: гибрид, конвейер, Пила, Труппа | п.1–2, 6, 8–9, 11–12 |
| **IV. Пауза и ночь** | мастерская: варка, оседание, Паганель, Пифия, Гефест | п.7, 10, 16–18 |
| **V. Глава и книга** | лог сессии, Редактор, Цензор, «Моя книга», эпилог | п.13 (книга) |
| **VI. Постоянные рамки** | язык, наследие, мир-антагонист, три базы, сценарная рамка | п.3–5, 15, 19–21 |

Зачем круг, а не каталог механик. Книга — последовательность состояний: сначала есть станок, потом рождается мир, потом идут ходы, потом ночь варит утро. Каталог механик не показывает, когда какая механика включается; круг жизни книги показывает.

Круг замыкается: ночь варит утро следующей главы, сессия ложится в книгу. Номера пунктов 1–21 сквозные и стабильны, ссылки «п.N» работают по всем документам. Пункт 13 живёт в двух местах круга — рождение мира (часть II) и глава/книга (часть V), это указано в заголовках.

## 4. Роли

Имена ролей функциональные, не личности. Исполнитель каждой роли — код или модель (правило исполнителя). Человек-владелец в операционном контуре запрещён: он архитектор, видит журналы и UI пост-фактум и вмешивается распоряжением — политика, пороги, заказы мастерской.

| Роль | Контур | Что делает | Артефакт | Пункт |
|---|---|---|---|---|
| **Челнок** | живой ход | подача рутины из банка, 0 генерации | готовая фраза | п.1, 3 |
| **Ткач** | живой ход | живая модель: уникальное и эмоциональное | проза сцены | п.1, 2 |
| **Селектор** (бывш. Драматург) | живой ход | тип действия, стоп-краны, держащий крючок | план действия | п.11, 21 |
| **Пила** | живой ход | диспетчер глубины; советник, не судья | вердикт «ткач/банк» | п.6 |
| **Цензор (живого хода)** | живой ход | словарная цензура всего живого | пропуск/брак | п.12 |
| **Паганель** | мастерская | картограф: места, пути, известность | кольца/коридоры | п.16 |
| **Пифия** | мастерская | предсказатель реплик (читает игрока) | карта игрока, гороскоп | п.17 |
| **Гефест** (Forge) | мастерская | кузнец: банки, переплавка, гороскопы | банки, заготовки | п.18 |
| **Авто-критик** | мастерская | функция Гефеста: ревью, уровень доверия | вердикт доверия | п.10 |
| **Цензор при варке** | мастерская | чистит банки один раз на выходе варки | чистый банк | п.4, 18 |
| **Редактор** | батчем | грамматика/пунктуация глав, аннотация | список правок | п.13 |
| **Цензор правок** | батчем | проверка правок Редактора (код, 1:1) | одобрено/брак | п.13 |
| **Толмач** | сборка пакета | разовый перевод сида (убран из живого хода) | языковой раздел | п.4 |

Зачем правило исполнителя. Гейт без названного исполнителя — дефект канона: неясно, кто чинит сбой и кто отвечает за результат. Назначение исполнителя (код или модель) закрывает это отверстие; человека сюда не ставят никогда.

Пример. Пила на пике советует Ткача. Исполнитель совета — код (переменная глубины), исполнитель решения — Селектор; владелец тут не участвует, и ход не ждёт чьего-либо согласования.

**Ткацкий словарь неприкосновенен:** станок, челнок, полотно, нити, пряжа.

## 5. Слои моделей и машин

```
Станок (локально):
  :5001 — генерация, 3B q4, ~5.6 ток/с (глубокие сцены; поднимается по надобности)
  :5002 — эмбеддинги BGE-M3, dim 1024 (резидент живого контура, ~2.4 ГБ)
  лемматизатор пакета — pymorphy3, ~100 МБ, миллисекунды на реплику

Внешний контур (слоты сменные):
  Ткач и Редактор прозы — литературная модель (CPU не тянет серьёзную)
  Глубокий разбор первой реплики — один дешёвый вызов LLM
  Паганель — большой внешний LLM на ключе владельца (UI-карточка)

Сменный слой (п.14): роли и интерфейсы фиксированы каноном,
имена моделей — «текущая реализация», заменяемы без правки канона.
Три пресета: локально-слабая / локально-средняя / внешние API.
```

Зачем сменный слой. Канон фиксирует роли, интерфейсы и требования, но не имена моделей (п.14): состав на сегодня — реализация, заменяемая без правки канона. Серьёзная литературная модель на CPU не живёт (4 ядра, без GPU, потолок ~3B q4), поэтому Ткач и Редактор прозы вынесены во внешний контур; локальный станок держит только то, что помещается в эти ограничения.

Требования к любой конфигурации: формулировки банка стабильны — повторяемое выдаётся одинаково (п.3); при отказе внешнего слота ход деградирует до локальной запаски, игра не умирает; словарный контроль языкового пакета не зависит от слота (п.9). Три пресета: «локально — слабая машина» / «локально — средняя» / «внешние API», дефолт — локальный.

Пример. На пресете «локально-слабая машина» Ткач работает на станке :5001 и пишет пиковую сцену при ~5.6 ток/с (рабочее значение) — отсюда 30–60 с на глубокую сцену. На пресете «внешние API» тот же Ткач идёт во внешнюю модель по ключу владельца; если провайдер отвалился, слот деградирует на локальную запаску, ход доставляется.

Транспорт: Telegram (Bot API, реплика целиком по Enter; канал, решающий NAT исходящим соединением) и web (WSS через cloudflared, только исходящие соединения, без открытых портов). WebRTC отвергнут: сигнальному серверу и TURN всё равно нужен публичный адрес, вес без пользы.

## 6. Три базы

Принцип «три хозяина — три базы»: каждой базой владеет один хозяин, пишет в неё только хозяин, остальные читают. Хозяева разные — разработчик станка, мастерская мира, сама игра.

| База | Хозяин | Пишет | Читает живой ход | Отвечает на вопрос |
|---|---|---|---|---|
| **base.db** | разработчик (при сборке) | только разработчик | read-only | «какие большие истории умеет станок» |
| **literary.db** | мастерская мира | Гефест + оседание (через Цензора) | да (банки) | «из какой пряжи мир одевает сцены» |
| **world(name).db** | игра | движок + игрок | да (основная) | «что реально случилось в этом мире» |

Зачем один хозяин у базы. Если писателей несколько, при расхождении фактов непонятно, чьи данные верны. Правило одного хозяина убирает вопрос: source of truth живого хода — `world(name).db`, при расхождении фактов мир главнее банков.

Внутри `world(name).db` действует правило писателей TNS35: одна таблица — один писатель. Forge трогает только `places`, `routes`, `world_meta`; остальные таблицы пишет runtime.

Пример. Паганель нарисовал дорогу в `places` (provenance='paganel'). В той же сцене живой ход увидел, что дорогу размыло дождём, и записал событие в `events`. Факт дороги живёт в `places` (пишет Паганель), факт размыва — в `events` (пишет runtime); `literary.db` при этом не изменилась.

## 7. Родословная: TNS35 → TNS45 → TNS55 → TNS65

TNS65 наследует механическое ядро TNS35/TNS45 и заменяет архитектуру прозы. Рамка «0 LLM в живом контуре» из TNS55 заменена гибридом; закон «английский внутри» отменён.

### Что переходит целиком (п.15 + контракты)

- Контракты баз: literary-reader, world-db, WORLD_WRITERS, провенанс и статусы атласа (promise→draft→baked).
- State-First: текст не переписывает outcome.
- Конвейер как последовательность шагов с гейтами.
- Forge CLI: parse / chunk / embed / create-world / materialize / snapshot (~60% импортируется как есть).
- Паганель (forge/edge.ts, forge/paganel/client.ts — тесты зелёные).
- Юнгианский профилировщик (14 метрик), :5002, фасад :8000, сегментные часы.
- Механики симуляции целиком: экономика (общая, NPC, рабовладельческая), здоровье и физиология, романтические профили, соцграф всех форматов, event sourcing (реплей и снапшоты), deferred hooks, world validator, start resolver, диалоговый менеджер.

Зачем наследовать целиком. Пункт 15 задаёт правило: механики весов, статов и структур мира — источник разнообразия; потеря в этом классе не допускается, отказ от конкретной механики — только явное решение владельца.

### Что заменено

| Было (TNS45 Big Six) | Стало (TNS65) |
|---|---|
| Драматург | Селектор |
| Актёр | голосовая карточка + банк реплик / Ткач |
| Проверяющий | TS-фильтры, словарь, механика |
| Стилист | микростиль + модуляция / Ткач |
| Цензор | словарь (двойной: ход + варка) |
| Хронист | триггеры БД, event sourcing |
| 6 LLM-вызовов (≈5 мин) | гибрид: 0 (рутина) или 1 (пик) |
| «0 LLM» TNS55 | гибрид: уникальное — живой Ткач |
| «English inside» | язык — упаковка данных, пакеты |
| Big Six — единственный маршрут | два пути текста в одном ходе |

Зачем замена. Шесть LLM-вызовов на ход давали живой замер ≈5 мин (канон родословной); чистый выбор из банков TNS55 укладывался в ≤2 с, но убивал уникальное и эмоциональное. Гибрид держит оба: рутина — 0 вызовов, пик — один.

### Что порезано (не переезжает)

narrative-bootstrapper, story-planner, director-loop, villain-manager, user-agent, researcher-agent, crafter-agent (открыт), Библия как сущность, wiki-механика, Юбилей, cross-world-bus, feature-flags, мёртвый intelligence/*.

### Миграция 55→65 (11.10)

1. Рамка «0 LLM в живом контуре» → **гибрид** (п.1).
2. Закон «английский внутри» **отменён**: ядро универсально, **язык — упаковка данных, не архитектура**; рабочий язык мира — язык игрока; книги-источники варятся на своём языке.
3. Словарная механика переезжает в **языковой пакет** (п.4, 14).
4. Толмач уходит из живого хода; перевод — операция сборки пакета.
5. Большой прогон «всё сразу» → варка по релевантности.

## 8. Контракты данных TNS35 — точка отсчёта

Код TNS35 живой и служит точкой отсчёта: контракты наследуются указателями, не копированием.

**literary.db** (9 таблиц): worlds, works, chunks (+ text_en + vectors), styles, personas, templates, quests, world_drafts. Пишут только Forge и ревью; рантайм открывает строго readonly.

**world.db** (22 таблицы): faces, relations (6 слоёв), npc_memory, entities, places/routes (provenance: book/generated/external/paganel/hearsay; status: promise→draft→baked), world_clock, deferred_events, events, runtime_gaps, quest_journal, экономика, player_profile, world_meta, sessions, graph, npc_state.

**WORLD_WRITERS**: forge — places, routes, world_meta (данные при рождении мира); runtime — остальные 19 таблиц.

**Рантайм TNS35** (RoleplayEngine): конвейер State-First Intent → Simulation → State → Context → Prose, 12 шагов хода. Двухконтурность: узоры + реакция агентов → runtime_gaps. Фасад :8000, Telegram-мост, :5001, :5002.

Зачем эта точка отсчёта. Контракты проверены живым кодом (literary-reader, world-db, world-writers, провенанс и статусы атласа); переписывать их заново — значит заново искать те же дыры. Поэтому TNS65 наследует контракты целиком и явно фиксирует только отличия.

### Отличия TNS65 от этой точки отсчёта

1. **base.db** — новая движковая база нарративов (в TNS35 не было).
2. **literary.db переезжает** из папки движка в папку мира (в TNS35 была одна на всё).
3. **Пачка персонажей** при рождении мира (96 карточек).
4. **Публикуемая книга игрока** как сторона игрока в world(name).db.

## 9. Потоки данных — сводка

```
Сборка движка:     разработчик → base.db (+ векторы); сид → языковой пакет
Рождение мира:     анкета → world(name).db; сид пакета → literary.db;
                   пачка 96 карточек → world(name).db;
                   якорь = ближайший нарратив base.db к синопсису (векторы, без LLM)
Живой ход:         реплика → конвейер (леммы, векторы, предвыбор, биндер)
                   → Челнок | Ткач → подтверждение → world(name).db
Пауза/ночь:        очередь ковки → Гефест → literary.db (через Цензора)
                   Паганель → world(name).db (places/routes)
                   оседание → literary.db (уровни доверия)
                   дрейф якоря: чтение обеих баз, сверка векторов
Глава/книга:       лог сессии (world) → Редактор → Цензор правок
                   → публикуемая книга (world, сторона игрока)
```

Зачем сводка в одном месте. Права записи разбросаны по ролям и контурам; одна схема показывает, кто куда пишет на каждом этапе жизни книги, и служит проверкой: если поток требует записи мимо хозяина базы, в проектировании ошибка.

## 10. Неизменные ограничения архитектуры

Каждое ограничение — не пожелание, а следствие довода. Ниже для каждого: что запрещено, почему, и чем обернётся нарушение.

**1. Человек-владелец не в операционном контуре (правило исполнителя).**
Довод: каждый гейт называет исполнителя — код или модель; гейт без исполнителя — дефект канона. Человек в контуре превращает каждый ход в ожидание распоряжения.
Пример последствий: если бы владелец подтверждал коммиты, пиковая сцена ждала бы ответа дольше, чем длится генерация; ход игрока превратился бы в согласование, а критерий успеха книги стал бы недостижим.

**2. Стоп-кран: неподтверждённое в мир не пишет (п.9, 11).**
Довод: предварительный путь (гипотезы, предвыбор, ветки) только читает и готовит; запись раньше подтверждения ломает State-First — в базу попал бы непроверенный смысл.
Пример последствий: гипотеза намерения «отпустить к матери» и заготовленная ветка ответа существуют до подтверждения. Если записать их сразу, а словарь потом опровергнет гипотезу, в `world(name).db` останется ложь о намерении игрока, и дальнейшие сцены будут строиться на ней.

**3. Живой ход пишет только в world(name).db (п.20).**
Довод: `world(name).db` — оперативная база мира и source of truth живого хода; остальные базы у живого хода на чтении.
Пример последствий: если бы Челнок писал выданную фразу в `literary.db`, рутина плодилась бы дублями и смешивалась с заготовками варки — банк перестал бы быть банком.

**4. literary.db в живом ходе не меняется никогда.**
Довод: судьбу живых сцен решает конвейер оседания в мастерской (п.10) — проверки живого хода, очистка от фактов, дедуп, авто-критик, уровень доверия. Живой ход этих проверок не даёт.
Пример последствий: удачная сцена с именем «Гаврил» ушла бы в банк как есть, и следующая заготовка носила бы чужое имя — граница «заранее / живьём» (п.2) сломана.

**5. Ход игрока приоритетнее фоновой варки (п.7).**
Довод: варка возобновляема (шаг — единица планирования), ход игрока — нет; ход ждать не может, варка может.
Пример последствий: очередь ковки пробуждения прервана приходом игрока. Если бы варка шла вперёд, ответ ждал бы конца шага; незавершённый шаг либо потерялся бы, либо вторгся бы в живой ход.

**6. Текст не переписывает состояние (State-First).**
Довод: outcome считает код (симуляция, вероятности, stateChanges), модель только проговаривает готовое. Иначе дрейф модели меняет канон книги.
Пример последствий: здоровье героя 41/50 — факт `world(name).db`. Если бы Ткач мог написать «рана затянулась» и это изменило стат, одна красивая фраза сломала бы физиологию и экономику мира.

**7. Канон фиксирует роли и интерфейсы, не имена моделей (п.14).**
Довод: имена моделей — «текущая реализация»; замена модели не должна требовать правки канона, иначе канон пришлось бы переписывать при каждом обновлении железа.
Пример последствий: замена BGE-M3 на другую embedding-модель меняет конфигурацию :5002, но не контракт «вектор смысла»; правка канона не нужна.

**8. Hermes самостоятельно модели не качает (п.14).**
Довод: загрузка — только по явному запросу владельца; штатный канал — раздел управления моделями UI. Принцип «только исходящие» соединения сохраняется, но инициатива остаётся за владельцем.
Пример последствий: при первом запуске с пустым кэшем моделей станок не уйдёт в Hugging Face сам; владелец ставит модель из UI, и только после этого слот работает.

**9. Ткацкий словарь неприкосновенен (п.18).**
Довод: термины закреплены `GLOSSARY.md`; выдуманные слова и метафоры для технических состояний запрещены, новый термин вносится в словарь, а не в текст мимо него.
Пример последствий: замена «живого хода» на жаргонное прозвище вывела бы текст из словаря — документация перестала бы сходиться с каноном, ссылки «п.N» и имена ролей разъехались бы.
