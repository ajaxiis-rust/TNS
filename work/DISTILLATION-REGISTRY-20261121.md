## Лист 2. Карта кода

**Состав и индекс.** `gograph build . --precise` — exit 0 (455 файлов Go разобрано). `go list ./...` — 39 пакетов; в `engine/internal` и `engine/cmd` — 466 файлов `*.go`, из них 256 без тестов; всего под `engine/` — 479 `*.go`.

**Методика.** Обёртка `/tmp/wrapcov.sh` выставляет `GOCOVERDIR` и `GOFLAGS=-cover` и передаёт исполнение дальше; прогон — `go test -tags e2e -exec /tmp/wrapcov.sh ./e2e -run '^TestINTN$' -count=1` с отдельным каталогом `/tmp/cov-intN`, затем `go tool covdata textfmt -i=/tmp/cov-intN -o /tmp/cov-intN.txt`. В сообщество механики взяты файлы `tns65/...` со счётчиком больше нуля (третья колонка профиля), пути в таблице переписаны от `engine/`. Обычный `-coverprofile` не работает: тесты сами собирают отдельный бинарник через `go build` внутри прогона.

**Что метод не видит.** `GOFLAGS=-cover` при `go test` покрывает только пакет `e2e`; файлы движка попадают в профиль из подпроцесса, собранного `go build` внутри теста. Поэтому код, который тест вызывает в своём процессе, в профиль не входит: `book.ApplyPlayerEdits` в int6, `book.*` с `testkit.NewClock`/`NewFakeSlot` в int7–int9. Профили int1, int6, int7, int8 и int9 совпадают по составу файлов — 34 файла шага `world birth`; механики в них нет. Для этих строк сообщество дополнено юнит-прогонами `internal/book` (72.8 % пакета), `internal/censor` (76.8 % пакета) и помечено «+ юнит». Демоны, убитые сигналом, покрытие не сбрасывают. В int2, int3, int4, int5, int10 и int11 серверный путь в профиле есть (54–88 файлов); в int1 и int6–int9 профиль ограничен шагом `world birth` (34 файла), потому что остальная работа идёт в процессе теста. ### Калибровка правила

**Числа.** Всего строк — 27; ложных — 14; спорных — 1; настоящих — 8; непрогон int1 (d) — 4. По типам: a — 10 строк (ложных 9, настоящих 1), b — 5 строк (ложных 2, настоящих 2, спорных 1), c — 8 строк (ложных 3, настоящих 5), d — 4 строки (ветки есть, int1 их не гонит: переигровка isekai, `world list`, UI-маршруты анкеты, `source_book`).

**Что даёт ложные срабатывания.**

1. **Тип a, покрытие от инициализации пакета** (строки 3, 4, 5, 7, 9). Файл попадает в профиль потому, что пакет слинкован и его инициализаторы исполнились один раз; блоков алгоритма рождения нет ни одного. Признак: count=1 у блоков `init` и у инициализаторов пакетных переменных, при нулевых блоках маршрутов и функций. Уточнение правила: задетость считать только по блокам, исполненным после входа в шаг рождения; блоки инициализации и конструкторы пакета не считать.
2. **Тип a, зависимость прямо названа каноном** (строки 2, 8, 10). Очередь мастерской (B-03.6), разведка Паганеля (B-14.4) и лемматизатор синопсиса (общий контракт `Lemmatizer` с резкой реплики) — не чужая механика, а поручение канона. Уточнение: файл чужого пакета, который канон прямо поручает рождению, относить к инфраструктуре.
3. **Тип a, испытательная обвязка** (строка 6). Файлы с `//go:build e2e` и подставные заглушки — принадлежность прогона, не механики.
4. **Тип b, замороженное или широкое имя** (строки 12, 13). `ancketa.go` и `geo_seed.go` названы в «Создаётся» своих задач (T-02-01, T-02-16); расхождение косметическое и правке не подлежит. Уточнение: сравнивать имя с «Создаётся» задачи; b-строка заводится только при обратном обещании (чтение в имени, запись в теле — строка 11) или при механике, которой в каноне нет (строка 14).
5. **Тип b, интерфейс по месту потребления** (строка 15). Файл-интерфейс без реализации — обычная практика, а не подмена имени.

**Уточнения правила, снимающие шум.** Разделить тип c на три вида: c1 «файла нет в движке» (строка 19), c2 «файл есть, прогон не задействует» (строки 17, 18, 20, 21), c3 «шаг без измерения» (строки 22–24). ### Вердикт по пилоту

1. Метод годится: на одной механике, 34 файлах сообщества и 14 шагах канона он дал 27 строк, из них 12 настоящих, и заполнил все три типа.
2. Главную ценность дают типы c и b: «шаг без измерения» (якорь, заказы, разведка) и «обратное обещание имени» (`world_readonly.go` пишет в `world_meta`) не видны по списку файлов и требуют решения, а не правки кода.
3. Тип a в нынешней формулировке шумит: 9 из 10 строк объяснимы инициализацией пакета, испытательной обвязкой или прямым поручением канона.
4. Для остальных механик правило брать с уточнениями: c делить на c1, c2, c3; a проверять по исполненным блокам алгоритма; b сверять с «Создаётся» задачи; источником шага считать атом `fine/04-spec` и задачу `fine/plan`, DOCS — ориентиром.
