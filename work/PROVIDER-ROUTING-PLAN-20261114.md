# Маршрутизация внешних провайдеров по задачам

Статус: дизайн, 2026-11-14. Решения владельца: сначала план; внутри списка задачи — ротация по кругу с откатом; `local` — последним в цепочке чата; карта книги-источника — отдельный проход и отдельный маршрут; один список на задачу, одну модель на кусок. Код не начат.

## 1. Что хочет владелец

- Игрок выбирает модель из списка и вставляет свои ключи.
- Запросы идут по его списку провайдеров по очереди, с откатом: быстрее и дешевле.
- Разные задачи — разным провайдерам. Ответы владельца (2026-11-14):
  1. `local` разрешён последним элементом цепочки чата — ход не пропадает, если все провайдеры отказали.
  2. **Обработка источников** и **литературная обработка готовой главы** — разные задачи: разные модели, разные промпты, разные настройки. Это два отдельных маршрута, а не один «книги».
  3. **Разведка Паганеля** — это исследование. В обработке сырых источников — выписка мест и времён, подготовка карты при варке книги-источника (например, для фанфика). В игре — отдельная задача, привязанная к местности и времени; маршрут зависит от селектора режима походов: реальный мир, вымышленный или смешанный.
  4. **Карта книги-источника — отдельно.** Книга всё равно парсится: если находятся названия, они сохраняются в таблицы разбора (`book_place`, `book_scene`). Картограф берёт их **отдельным проходом** — это глобальная разведка, отдельный маршрут.
  5. **Один список на задачу, одна модель на кусок.** Внутри `sources` и `editor` роль-уровневой маршрутизации нет; кусок текста заполняет одна модель за один запрос.
  6. **Внутри `editor`** отдельного деления на `editor` / `editor_digest` / `style` нет: один список на литературную обработку главы.

## 2. Текущее состояние (факты кода)

- Реестр провайдеров и цены — `engine/providers.toml` (`internal/providercfg`), ключи и выбранная модель — `settings.toml` (`<имя>`, `<имя>_model`).
- Чат (Ткач) собирает **один** слот на старте ядра: `DefaultChatWeaver` (`internal/webapi/chat_weaver_pack.go`) по `slots.default` из `config.yaml`; смена провайдера — правка конфига и перезапуск.
- Мастерская (`internal/workshop`) ходит через `slotForProvider` / `workshop.SetSlot`, но в проде `SetSlot` не вызывается: генерация книг сейчас не подключена к модели (P4). `model_bindings` заполняются, но рантайм их не читает.
- Роли мастерской уже названы в коде: `forge-book` (варка книги-источника), `editor` и `editor_digest` (Редактор главы и дайджест), `style` (стилизация), `compose`, `epoch`, `horoscope`, `pythia`, `cast-role`, `forge-card`.
- Паганель-разведка (`internal/paganel/scout.go`) — заглушка `GET http://paganel.example/research`; к модели не подключена, `key_ref` из `config.yaml` не используется. Режимы походов и роли разведки описаны в документации (см. §14).
- Рейтинг 18+ уже запрещает внешние слоты: `workshop.ProviderForRating` возвращает `local`.
- Счётчики вызовов: `engine/state/usage.jsonl`, строки `{role, calls, tokens, cost_millis}` (`models.AppendUsage`), читаются монитором и карточками.
- Таблиц глубокого разбора в коде ещё нет: миграции литературной базы заканчиваются `0005_cast.sql`, `book_place`/`book_scene` живут в спеке (`fine/04-spec/05-workshop.md` W-26) и плане P13 (`fine/plan/14-book-deep-read.md`, миграция 0006). Карта книги-источника опирается на них.

## 3. Термины

- **Провайдер** — запись `[[providers]]` в `providers.toml` (имя = ключ в `settings.toml`).
- **Модель** — выбранная игроком модель провайдера (`<имя>_model`, иначе `default_model`).
- **Маршрут** — упорядоченный список имён провайдеров для задачи.
- **Задача** — единица настройки маршрута; внутри задачи список один, роль-уровневых списков нет:
  - `chat` — Ткач, живой ход;
  - `sources` — обработка источников: разбор и варка книги-источника (`forge-book`, анализ P13, извлечение фактов, цензор при варке);
  - `sources_map` — карта книги-источника: отдельный проход картографа по местам и временам, выписанным при разборе (глобальная разведка);
  - `editor` — литературная обработка готовой главы: Редактор, дайджест главы, стилизация (`editor`, `editor_digest`, `style`);
  - `scout_real`, `scout_fiction`, `scout_mixed` — разведка Паганеля в игре по режиму походов мира.
- **Промпт и настройки роли** — не в маршруте: остаются у роли (`model_bindings`, `world_meta` `role.<роль>`: температура, промпты, приоритет). Маршрут выбирает только провайдера и модель.

## 4. Данные игрока

Маршруты — в `settings.toml` плоскими ключами (формат файла не меняется, UI уже умеет писать произвольные ключи):

```toml
deepseek = "sk-..."
deepseek_model = "deepseek-chat"
mimo = "sk-..."
mimo_model = "mimo-v2-flash"
gemini-flash = "..."
gemini-flash_model = "gemini-3.8-flash"

route_chat = "deepseek,mimo,gemini-flash,local"
route_sources = "mimo,qwen"
route_sources_map = "gemini-pro,deepseek"
route_editor = "gemini-flash,deepseek"
route_scout_real = "gemini-flash"
route_scout_fiction = "mimo"
route_scout_mixed = "gemini-flash,deepseek"
```

Правила:

- Порядок в строке — порядок ротации. Нет ключа/строки — задача берёт запасной маршрут: `route_chat` → `slots.default`, `route_sources`/`route_editor` → `slots.default`, `route_sources_map` → `route_sources` → `slots.default`, `route_scout_*` → разведка выключена.
- Единица запроса — кусок текста целиком: провайдера выбирает роутер, но кусок обрабатывает одна модель за один запрос; дробление куска между провайдерами и частичная переотправка запрещены.
- Допустимы только имена из `providers.toml`; неизвестное имя — 400 при сохранении, а не молчаливое выпадение.
- `local` разрешён последним элементом цепочки (подтверждено владельцем); в середине — предупреждение в UI.
- Модель берётся из `<имя>_model`; у каждого провайдера своя. Один провайдер в маршруте — одна модель.
- Ключ пустой — провайдер пропускается при выборе; если пропущены все — деградация по правилам задачи.
- Режим походов (`travel_mode`: реальная/вымышленная/смешанная) задаётся полем анкеты рождения и не выводится из жанров (`fine/04-spec/03-birth.md`, `fine/plan/06-paganel.md`). Маршрут `scout_*` выбирается по этому полю активного мира.

## 5. Роутер

Новый пакет `internal/providerroute` (без зависимостей от webapi):

- `Route` — список имён; `Router` — маршруты по задачам + атомарные курсоры.
- Выбор на запрос: `calls(task) % len(alive)` — первый провайдер, затем следующие по кругу. Курсор в памяти процесса, сбрасывается при перезапуске (в тестах — подменяемый).
- Гранулярность ротации — запрос: следующий запрос (следующий кусок или глава) уходит следующему провайдеру. Один кусок — один провайдер и один запрос.
- Откат: на ошибку соединения, тайм-аут, 429, 5xx, отказ ключа (401/403), `netgate.ErrDeniedHost` — следующий провайдер.
- Не откатывать: 400 «плохой запрос», отказ цензора по содержанию, ошибку после первого отданного чанка (повтор дал бы дубль прозы); ход идёт по существующей деградации (`slot.degraded`).
- Все провайдеры отказали: чат — `fallbackReply` и путь `fallback`; источники/редактор — лестница `GenerateWithRetry` и `ErrForgeDegraded`; разведка — пропуск, ход не блокируется.
- 18+: маршрут принудительно `local`, внешние провайдеры не вызываются.
- Стоимость/лимиты: каждый вызов пишется в `usage.jsonl` с полем `provider` (старые строки без поля читаются как раньше). Ротация распределяет лимиты; цена не сортируется (порядок задаёт игрок).

## 6. Точки подключения

### 6.1 Чат (этап P1)

- `DefaultChatWeaver` собирает `RoutedProseSlot` (`turn.ProseSlot`): на каждый `Stream` роутер выбирает провайдера, строит/берёт из кэша клиент (`models.ProviderClient` / `models.OpenAIClient`) и стримит. Ошибка до первого чанка — следующий провайдер; после первого — как сейчас.
- Ключи, модели и маршрут читаются на старте; изменения применяются после перезапуска. В UI — предупреждение.
- Путь хода остаётся «weaver»; откат пишется событием журнала (§8), `slot.degraded` — только при полном отказе.

### 6.2 Обработка источников (этап P3)

- Маршрут `sources`, адаптер `RoutedWorkshopSlot` для `workshop.Slot` (`Generate(ctx, role, prompt)`).
- Роли: `forge-book` (разбор/варка книги-источника), анализ P13, извлечение фактов и словарей, цензор при варке. Промпты и температура — у роли, не у маршрута.
- Один список на задачу: роль-уровневой маршрутизации нет (решение владельца). Кусок текста приходит одной модели одним запросом целиком; ротация — между запросами, то есть между кусками.
- Места и времена при разборе пишутся кодом в таблицы глубокого разбора `book_place` / `book_scene` (W-26, миграция 0006); карту по ним строит картограф отдельным проходом (§6.5).
- Подключение: `workshop.SetSlot(...)` в `cmd/tns65/main.go` (сейчас не вызывается). Это одновременно закрывает P4-проводку слота мастерской; без неё маршрут источников не проверить.

### 6.3 Литературная обработка готовой главы (этап P4)

- Маршрут `editor`, те же `RoutedWorkshopSlot`, роли `editor`, `editor_digest`, `style`.
- Отличие от источников: другие промпты (правка 1:1, краткое содержание, стилизация), другие настройки роли; модель может быть другой. Маршрут `editor` независим от `sources`.
- Редактор правит только орфографию и пунктуацию (списком «было → стало»), Цензор правок проверяет 1:1 — это не меняется.

### 6.4 Разведка Паганеля в игре (этап P5)

- Заменить заглушку `Scout.Fetch` на реальный вызов модели; маршрут выбирается по `travel_mode` активного мира:
  - `scout_real` — Летописец: реальным мирам можно наружу, земля из справочников эпохи;
  - `scout_fiction` — Картограф вымысла: наружу нельзя, земля берётся из голоса книги;
  - `scout_mixed` — Смешанный/Штурман: книжные точки ложатся на реальный холст, направление точное.
- Сохранить бюджет сессии (~3 вызова), тайм-аут ~30 с и правило «пропуск не блокирует ход».
- `key_ref` в `config.yaml` остаётся ссылкой на ключ по умолчанию, если маршрут пуст.

### 6.5 Карта книги-источника: глобальная разведка (этап P6)

- Отдельная задача и отдельный маршрут `sources_map`. При разборе книги код уже выписывает имена мест и времена в `book_place` / `book_scene`; картограф берёт эти таблицы **отдельным проходом** и сводит их в карту книги-источника.
- Проза заново не читается: вход прохода — таблицы разбора, а не текст книги. Это отличает проход от `sources`, где модель работает с текстом кусков.
- Роли картографа — по режиму походов, как в игре (§6.4): Летописец / Картограф вымысла / Штурман. Промпты, температура и формат ответа — у роли.
- Зависимость: таблиц глубокого разбора в коде ещё нет (P13, миграция 0006). До неё маршрут можно сохранить в настройках, но вызовов не будет.
- Если `route_sources_map` не задан — падение на `route_sources`, затем на `slots.default`.

## 7. API

- `GET /api/providers/routes` → `{"routes":{"chat":[…],"sources":[…],"sources_map":[…],"editor":[…],"scout_real":[],"scout_fiction":[],"scout_mixed":[]},"warnings":[…]}`.
- `PUT /api/providers/routes` `{"task":"sources","providers":["mimo","qwen"]}` → проверка имён и дублей, запись `route_<task>` в `settings.toml`, ответ `{"status":"ok","restart_required":true}`.
- Ошибки: `bad_request` (неизвестный провайдер, дубль, `local` не последним), `internal` (запись файла).
- `GET /api/providers` расширяется полем `routes` (какие задачи используют провайдера), чтобы карточка показывала участие в маршрутах.

## 8. Наблюдаемость

Новые константы журнала (`internal/journal/events.go`, список в DOCS/10 §6):

- `route.changed` — сохранён маршрут задачи (task, order).
- `provider.rotate` — выбран провайдер по кругу (task, provider, index).
- `provider.failover` — откат (task, from, to, error).
- `provider.exhausted` — все отказали (task, errors_count).

`usage.jsonl`: поле `provider` (необязательное), чтобы монитор показывал расход по провайдерам; строки без поля — «unknown».

## 9. UI

В разделе «Провайдеры» — блок «Маршруты» над карточками:

- Задачи: «Чат», «Обработка источников», «Карта книги-источника (глобальная разведка)», «Литературная обработка главы», «Разведка: реальный мир», «Разведка: вымышленный мир», «Разведка: смешанный».
- Для каждой — упорядоченный список: добавить провайдера из выпадающего списка, поднять/опустить, убрать. Показывать модель и наличие ключа; провайдер без ключа — приглушён и помечен, но выбрать можно.
- Подсказка: «Запросы идут по кругу; при ошибке — следующий. Изменения применяются после перезапуска движка».
- Пустой список — «не задан»: задача падает на запасной маршрут по правилам §4 (разведка — выключена).
- Для мира с рейтингом 18+ маршруты внешних провайдеров показываются как неактивные.
- Проверка текстов интерфейса: без «станк»/«станци» (существующий `TestUITextsWithoutStationSlang`).

## 10. Ограничения и риски

- Дублирование платных вызовов: повтор после первого чанка запрещён; откат только до первого чанка.
- Разные модели/форматы: один промпт к Gemini и к OpenAI-совместимым даёт разное качество; откат может дать стилистический скачок. В журнале видно, кто ответил.
- Ротация по кускам: соседние куски книги обрабатывают разные модели — извлечение может выйти неровным. Выравнивания нет; игрок ставит первым того, кого хочет видеть на большинстве кусков, журнал показывает провайдера на каждый запрос.
- Отдельный проход картографа добавляет расход на книгу — осознанно: он читает таблицы мест и времён, а не прозу.
- Лимиты: ротация помогает от 429, но не от общего бюджета игрока.
- Ключи: только `settings.toml` 0600, наружу не отдаются.
- Рейтинг 18+ — внешние маршруты не работают.
- Перезапуск: маршруты и ключи читаются на старте; live-правка только для карточек/списков (как сейчас).
- Разные задачи нельзя случайно смешать: `sources`, `sources_map`, `editor`, `scout_*` — отдельные ключи; UI не даёт сохранить один список под двумя задачами.

## 11. Тесты и гейты

- `providerroute`: ротация по кругу, пропуск без ключа, откат на каждой категории ошибок, отсутствие повтора после первого чанка, all-fail, изоляция курсоров задач, 18+ → local, `local` только последним.
- `turn`: `RoutedProseSlot` поверх двух фейковых провайдеров — ответ второго после ошибки первого.
- `webapi`: GET/PUT маршрутов для всех задач, валидация, запись `settings.toml`, `restart_required`, карточки с полем маршрутов.
- `workshop`: `RoutedWorkshopSlot` для `sources` и `editor` на фейках; кусок уходит одному провайдеру целиком, дробления между провайдерами нет; лестница не ломается; промпты ролей не меняются.
- `paganel`: карта книги строится по `book_place` / `book_scene` без повторного чтения прозы; `sources_map` при отсутствии маршрута падает на `sources`; маршрут по `travel_mode` (реальная/вымышленная/смешанная), бюджет/тайм-аут сохранены, при отсутствии ключей — пропуск.
- `go build ./...`, `go vet`, `go test` затронутых пакетов, `scripts/docs-check.sh`; UI — браузер на изолированном экземпляре (карточки, редактор маршрутов, сохранение, перезапуск).
- Известный флейк `internal/supervisor TestNoShortReadyBudget` не считать регрессией (воспроизводится на HEAD).

## 12. Этапы

1. **P1. Роутер + чат.** `internal/providerroute`, `RoutedProseSlot`, `DefaultChatWeaver` по `route_chat`, события журнала, usage.provider, тесты. Критерий: два провайдера с ключами, второй отвечает после ошибки первого; ротация видна в журнале.
2. **P2. API и UI маршрутов.** Все задачи (`chat`, `sources`, `sources_map`, `editor`, `scout_real/fiction/mixed`), блок «Маршруты», предупреждение о перезапуске. Критерий: игрок собирает списки, они сохраняются и переживают перезапуск.
3. **P3. Обработка источников.** `RoutedWorkshopSlot`, `workshop.SetSlot` в `main.go`, маршрут `sources` (`forge-book`, анализ, извлечение). Критерий: варка книги идёт через маршрут, при отказе — следующий провайдер; без ключей — текущая деградация.
4. **P4. Литературная обработка главы.** Маршрут `editor` для `editor`, `editor_digest`, `style`. Критерий: правка главы и дайджест идут выбранным провайдером, промпты и 1:1-проверка не изменились.
5. **P5. Паганель в игре.** Реальный вызов модели по `route_scout_<travel_mode>`, сохранение бюджета/тайм-аута. Критерий: разведка отвечает выбранным провайдером, при отсутствии ключей — пропуск, ход не блокируется.
6. **P6. Карта книги-источника.** Отдельный проход картографа по `book_place` / `book_scene` под маршрутом `sources_map`, роли по режиму походов. Критерий: карта строится по выписанным местам и временам без повторного чтения прозы; без `sources_map` — падение на `sources`. Зависит от P13 (таблицы разбора) и P3.

Каждый этап — отдельный коммит с тестами и правкой DOCS/10; P3–P6 затрагивают незавершённые узлы (P4-проводка мастерской, заглушка разведки, таблицы разбора P13) и требуют проверки на копии прода.

## 13. Решения владельца

Ответы 2026-11-14 (открытых вопросов не осталось):

1. `local` — последним в цепочке чата. **Да.**
2. Обработка источников и литературная обработка готовой главы — разные задачи, разные модели, промпты и настройки. **Раздельные маршруты `sources` и `editor`.**
3. Разведка Паганеля — исследование: в обработке источников выписка мест и времён и карта книги-источника; в игре — отдельная задача по местности и времени, маршрут зависит от режима походов. **Маршруты `scout_real` / `scout_fiction` / `scout_mixed`.**
4. Карта книги-источника строится отдельно: разбор сохраняет имена мест и времена в таблицы (`book_place`, `book_scene`), картограф берёт их отдельным проходом — глобальная разведка. **Отдельный маршрут `sources_map`.**
5. Внутри `sources` роль-уровневой маршрутизации нет. **Один список на задачу; одна модель заполняет кусок за один запрос** (как в механике краткого содержания: «один запрос, одна модель»).
6. Внутри `editor` отдельного деления на `editor` / `editor_digest` / `style` нет. **Один список на литературную обработку главы.**
